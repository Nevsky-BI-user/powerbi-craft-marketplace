# Розгортання нового PBIP-репозиторію

Мета — за один прохід отримати репозиторій, у якому вже діють правила роботи,
гейти й git-налаштування під специфіку PBIP, а не «порожній git, розберемось потім».

Скіл ідемпотентний: його можна запустити повторно на тій самій теці, щоб дозаповнити
§0 після того, як користувач збереже PBIP з Desktop.

---

## Ключовий принцип: не питати те, що видно у файлах

Опитування має бути коротким. Спочатку **розвідка**, і тільки потім питання —
про те, чого у файлах немає. Питати «який у вас формат звіту?», коли поруч лежить
`report.json`, — марно витрачений хід користувача.

---

## Фаза 0. Розвідка

Зібрати стан теки **до** будь-яких дій і до питань:

```bash
ls -a <dir>                                    # що вже є
git -C <dir> rev-parse --is-inside-work-tree   # чи вже репозиторій
git -C <dir> branch --show-current
git -C <dir> remote -v
gh auth status                                 # чи можна створити remote
```

Далі, якщо PBIP уже є:

| Параметр | Звідки |
|---|---|
| Назва проєкту | ім'я `*.pbip` |
| **Формат звіту** | є `<P>.Report/definition/pages/` → **PBIR enhanced**; є лише `report.json` → **PBIR-Legacy** |
| Версія `definition.pbir` | поле `version` |
| Розмір канви | Legacy: `sections[0].width/height`; enhanced: `page.json` |
| Тема | `config.themeCollection` у `report.json` |
| Культура моделі | `culture:` у `model.tmdl` |
| Наявність таблиць | `<P>.SemanticModel/definition/tables/` |

**Якщо PBIP ще немає** — це нормальний сценарій. Валідний PBIP надійно генерує лише
Power BI Desktop (*Файл → Зберегти як → Power BI project (.pbip)*), тому скелет
вручну не вигадувати. Розгорнути git і правила зараз, а параметри звіту в §0 лишити
як `[заповнити]` і сказати користувачу: збережеш проєкт з Desktop — поклич скіл ще
раз, він дозаповнить §0 з файлів.

### Що робити, якщо файли вже є

Наявні `CLAUDE.md`, `.gitignore`, `.gitattributes`, `.claude/settings.json`
**не перезаписувати мовчки**. Показати, чим шаблон відрізняється від наявного файлу,
і спитати: замінити / злити / лишити. Користувач міг щось туди дописати, і мовчазна
втрата цього — гірша за незастосований шаблон.

---

## Фаза 1. Опитування

Два раунди `AskUserQuestion` (максимум 4 питання на виклик) плюс одне текстове.
Пропускати питання, на яке розвідка вже дала однозначну відповідь.

### Раунд A — репозиторій і git

1. **Інтеграційна гілка** — `main` (рекомендовано) / `master` / `remote_dev` / інша.
   Від неї залежить §0 і правило «не комітити напряму».
2. **Remote** — створити приватний GitHub-репо (рекомендовано) / створити публічний /
   вже є URL / поки без remote.
   Створення репо — це публікація вмісту назовні, тому за замовчуванням **private**
   і тільки після явного вибору.
3. **Трекер задач** — Azure DevOps Boards (`TASK NNNNN:`) / Jira (`ABC-123:`) /
   GitHub Issues (`#123`) / немає.
   Визначає формат гілок `task/<NNN>` і префікс коміта.
4. **CLAUDE.md у git** — комітити (рекомендовано) / лишити локальним.
   Локальним — коли репо корпоративне й спільне з людьми, які AI-файли в ньому не хочуть.

### Раунд B — зміст проєкту

1. **Джерела даних** (multiSelect) — Azure Synapse / SQL Server / Fabric Lakehouse
   або Warehouse / Dataverse чи D365 / SAP / Excel чи файли / ще не визначено.
2. **RLS** — буде / не буде / ще не вирішено.
3. **Інкрементальне оновлення** — так, потрібні `RangeStart`/`RangeEnd` / ні / пізніше.

### Текстове питання

**Бізнес-домен звіту, одним реченням** — «HR-аналітика», «фінансовий P&L»,
«моніторинг обладнання». Іде в §0 і в README; варіантами не обмежується, тому
питати звичайним текстом, а не кнопками.

Не вигадувати значення за користувача. Якщо на щось немає відповіді —
у §0 лишається `[заповнити]`: чесний плейсхолдер краще за правдоподібну вигадку,
бо вигадку потім ніхто не перевірить.

## Фаза 2. Розгортання

Порядок має значення: git спочатку, файли потім, коміт останнім.

### 2.1 Git

```bash
git init -b <інтеграційна-гілка>     # лише якщо ще не репозиторій
```

Якщо репозиторій уже є — `git init` не запускати, гілку не перемикати.

### 2.2 Файли з `assets/`

| Шаблон | Куди | Призначення |
|---|---|---|
| `CLAUDE.md.template` | `CLAUDE.md` | правила, гейти G0–G4, довідник заборон |
| `gitignore.template` | `.gitignore` | локальний стан Desktop, секрети, ПДн |
| `gitattributes.template` | `.gitattributes` | eol, binary, `merge=ours` для згенерованих |
| `settings.json.template` | `.claude/settings.json` | allowlist read-only команд |
| `README.md.template` | `README.md` | що це, як відкрити, куди дивитись |
| `pull_request_template.md` | `.github/pull_request_template.md` | чекбокси гейтів G3/G4 |
| `../scripts/check-gates.ps1` | `scripts/check-gates.ps1` | автоперевірка гейтів (пер-типова матриця) |
| `../scripts/bpa-rules.json` | `scripts/bpa-rules.json` | правила BPA: Microsoft-набір (34) + хаус-правила (3) |
| `../scripts/check-model-refs.py` | `scripts/check-model-refs.py` | биті посилання DAX→таблиці (клас дефектів поза BPA) |

`.claude/settings.json` комітиться свідомо: `.gitignore` виключає `.claude/`, але
`settings.json` — це проєктні дозволи для команди, тому в шаблоні `.gitignore`
є виняток `!.claude/settings.json`. Не прибирати його.

### 2.3 Підстановка

У шаблонах плейсхолдери виду `{{PROJECT_NAME}}`. Замінити **всі**; жодного `{{`
не має лишитись — це перевіряється у фазі 4.

| Плейсхолдер | Джерело |
|---|---|
| `{{PROJECT_NAME}}` | ім'я `*.pbip` або назва теки |
| `{{BUSINESS_DOMAIN}}` | текстове питання |
| `{{INTEGRATION_BRANCH}}` | раунд A |
| `{{REMOTE}}` | раунд A → URL або «немає» |
| `{{TRACKER}}` | раунд A → напр. `Azure Boards, TASK NNNNN:` |
| `{{REPORT_FORMAT}}` | розвідка |
| `{{DATA_SOURCES}}` | раунд B |
| `{{CANVAS}}` | розвідка або `[заповнити]` |
| `{{THEME}}` | розвідка або `[заповнити]` |
| `{{CULTURE}}` | розвідка або `[заповнити]` |
| `{{RLS}}` | раунд B |

Якщо обрано «CLAUDE.md локальним» — додати `CLAUDE.md` окремим рядком у `.gitignore`
(рядок уже є в шаблоні закоментованим, просто розкоментувати).

## Фаза 3. Перший коміт

```bash
git -C <dir> add -A
git -C <dir> status --short          # переконатись, що локального нічого не потрапило
```

Перед комітом перевірити, що `.gitignore` реально працює:

```bash
git -C <dir> check-ignore -v <P>.Report/.pbi/localSettings.json
```

Порожня відповідь означає, що правило **не** спрацювало — типова причина
інлайн-коментар у `.gitignore` (git читає `#` лише на початку рядка). Полагодити
до коміта, а не після.

Коміт:

```
chore: bootstrap PBIP-репозиторію (правила, гейти, git-налаштування)
```

У тілі — що додано і **що перевірено** (це той самий стандарт, який CLAUDE.md вимагає
від усіх наступних комітів; bootstrap-коміт має його задавати, а не порушувати).

Це єдиний коміт, який лягає прямо в інтеграційну гілку — виняток описаний у §3.1
самого CLAUDE.md. Далі правило діє без винятків.

### Remote і push

Тільки якщо користувач обрав це в раунді A:

```bash
gh repo create <owner>/<name> --private --source=. --remote=origin --push
```

Якщо `gh` не авторизований — не намагатись обійти, а сказати користувачу, що потрібна
авторизація. Push у чужий наявний remote — окрема дія, потрібна пряма вказівка.

## Фаза 4. Самоперевірка

Скіл, який вимагає гейтів від інших, зобов'язаний пройти власний. Перед звітом
про завершення:

- [ ] `grep -c "{{" CLAUDE.md README.md` → **0** незамінених плейсхолдерів.
- [ ] `git check-ignore -v` ловить `localSettings.json` **і** `*.abf`.
- [ ] `git status --short` — чисто, локальні файли не в індексі.
- [ ] `git log -1 --stat` — у комі ті файли, що очікувались.
- [ ] Якщо створювався remote — `git status -sb` показує трекінг.
- [ ] `powershell -File scripts/check-gates.ps1` відпрацьовує без помилок
      (на порожньому проєкті частина перевірок пропускається — це очікувано).
- [ ] Якщо модель уже існує: BPA-гейт або пройшов, або його провал показано
      користувачу як беклог якості моделі (на легасі-моделі перший прогін
      майже напевно дасть Severity 3 — це очікувано; тюнінг: `scripts/bpa-rules.json`).

## Що сказати користувачу наприкінці

Коротко: що створено, куди запушено, і **три наступні кроки**:

1. Заповнити решту `[заповнити]` у §0 CLAUDE.md.
2. Якщо PBIP ще немає — зберегти проєкт з Power BI Desktop і покликати скіл ще раз.
3. Перед першою задачею — відгалузитись: `git checkout -b feature/<опис>`.

Окремо назвати те, що лишилось незаповненим, і чому — щоб це не виглядало як
«все готово», коли частина параметрів невідома.

## Опційно: блокуючий хук на коміт

`scripts/check-gates.ps1` можна повісити на `PreToolUse` для `Bash(git commit*)`,
щоб гейти не залежали від того, чи агент про них згадав. За замовчуванням **не**
вмикати: хибне спрацювання блокує роботу користувача, і це має бути його свідомий
вибір. Якщо просить — додати в `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "powershell -ExecutionPolicy Bypass -File scripts/check-gates.ps1 -Quiet"
          }
        ]
      }
    ]
  }
}
```
