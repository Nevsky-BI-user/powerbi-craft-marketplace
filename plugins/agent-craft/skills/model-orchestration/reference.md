# model-orchestration — reference

Розгорнуті умови застосування, шаблони і економіка. Скорочена версія — SKILL.md.

## §1. Формула рішення

**Рівень моделі = ціна помилки × неоднозначність. Не розмір задачі.**

- *Ціна помилки*: що станеться, якщо результат тихо неправильний? Публікація
  в canonical-репо, git-хук, що блокуватиме команди, DAX-довідник, з якого
  копіюватимуть роками, зміна схеми БД — дорого. Чернетка, чорновий переклад,
  внутрішня нотатка — дешево.
- *Неоднозначність*: скільки суджень треба ухвалити без чіткого критерію?
  Опис скіла (маршрутизація тисяч майбутніх запитів через 1000 символів) —
  високо. Спека за зразком з фікстурою з власних columnMetadata — низько.
- Детерміноване → **скрипт, не модель**: хеші, діфи, валідація JSON/YAML,
  масові заміни, підрахунки. Модель, що робить роботу скрипта, — і дорожча,
  і менш надійна.

## §2. Умови застосування оркестрації — детально

### Умови «за» (досить однієї сильної)

| # | Умова | Тест | Приклад із практики |
|---|---|---|---|
| 1 | ≥3 незалежні гілки | Чи можна сформулювати гілки так, щоб жодна не читала результат іншої? | Аудит: 2 проєкти + 4 бібліотеки + ринок — 9 агентів паралельно |
| 2 | Обсяг > контексту | Чи треба прочитати більше, ніж влазить і лишає місце для роботи? | 5 репозиторіїв, ~77 скілів |
| 3 | Незалежність суджень | Чи виграє результат від того, що оцінювач НЕ бачив процесу? | 4 скептики знайшли 29 дефектів у «готовій» роботі, включно з багом regex у git-хуку |
| 4 | Ціна помилки > ціни верифікації | Чи дорожче виправляти в проді, ніж заплатити за перевірку зараз? | Реліз у marketplace: 1 агент-скептик ≪ зіпсований реліз |
| 5 | N однорідних елементів | Чи можна написати ОДИН шаблон і критерій для всіх? | 12 spec-файлів фабрик; переклади описів |

### Контрумови (перекривають «за»)

| # | Контрумова | Чому | Що робити натомість |
|---|---|---|---|
| 1 | Coherence-критичний текст | N агентів = N стилів і неузгоджені терміни; для набору описів скілів узгодженість — сама суть | Одна голова пише; агенти постачають факти/чернетки |
| 2 | Задача < overhead | Запуск агента ≈ 10–15k токенів (бриф + системний промпт + читання контексту); правка на 2k токенів у делегуванні дорожчає в рази | Зробити в головному контексті |
| 3 | Немає механічного критерію приймання | «Зроби гарно» виконавцю = лотерея; переробіток з'їсть економію | Спершу сформулювати критерій; якщо неможливо — робити самому |
| 4 | Жива взаємодія | Користувач у діалозі; підагент не може перепитати користувача | Головний контекст веде діалог, делегує лише фонове |

### Прикордонні випадки

- **2 гілки**: паралелити можна, але виграш малий — вирішує стінний час
  (чекаєте на результат зараз → так; фонова робота → байдуже).
- **Довгий однорідний список (N>20)**: не 20 агентів, а конвеєр партіями або
  один агент у циклі зі скриптовою перевіркою після кожної партії.
- **Розвідка перед оркестрацією**: список робіт (які файли, які скіли) майже
  завжди дешевше зібрати самому (Glob/Grep), і лише потім фан-аутити роботу.
  Не делегуйте «знайди що робити» — делегуйте «зроби ось це».

## §3. Вибір рівня моделі

### Відносна вартість (звіряти з актуальним прайсом Anthropic; станом на 2026-08)

| Рівень (Claude Code alias) | Модель | Відносно Haiku |
|---|---|---|
| `haiku` | Haiku 4.5 | 1× |
| `sonnet` | Sonnet 5 | ~2× |
| `opus` | Opus 5 | ~5× |
| `inherit` (сесія на топ-моделі) | Fable/Opus | ~5–10× |

Другий важіль — **effort** (`low`/`medium`/`high`/`xhigh`/`max`) на тому ж рівні:
`low` для механіки ріже вартість і багатослів'я без зміни моделі; `high`/`xhigh`
для діагностики й верифікації. Спершу крутіть effort, потім рівень.

### Мапа задач Power BI-стеку → рівень

| Задача | Рівень | Чому |
|---|---|---|
| Діфи бібліотек скілів, валідація манифестів | скрипт | Детерміноване (sync_from_local.py, validate_repo.py) |
| Прогін тригер-проб корпусу, збирання результатів | haiku | Механіка за списком, перевірка — підрахунок збігів |
| Spec-файли за зразком, batch-конвертації, чернетки перекладів | haiku | Один шаблон, механічна перевірка (vitest / json.loads) |
| Read-only ревʼю за рубрикою (schema-reviewer, security-auditor, docs-drift-auditor) | sonnet | Судження є, але рубрика звужує; ціна помилки середня (звіт, не зміна) |
| Скаффолд компонента/фабрики, категоризація PR-змін | sonnet | Стандартні патерни, перевірка tsc+тестами |
| Написання/правка ОПИСІВ скілів | топ | 1000 символів керують маршрутизацією назавжди; максимальна неоднозначність |
| DAX-діагностика performance (FE/SE, CallbackDataID) | топ | Міркування, не шаблон; хибний діагноз = марна переробка |
| План зміни схеми БД; вибір архітектури | топ | Ціна помилки максимальна, відкат дорогий |
| Адверсарійна верифікація перед публікацією | топ (effort high/xhigh) | Скептик слабший за автора нічого не ловить |
| Фінальний синтез звіту/ревʼю | головний контекст | Coherence + відповідальність перед користувачем |

## §4. Бриф виконавця

### Шаблон (усі 6 полів обов'язкові)

```
МЕТА: <один абзац: що має існувати після твоєї роботи>
МЕЖІ: <що НЕ чіпати: файли, гілки, налаштування; "не розширюй скоуп">
ВХІД: <точні шляхи файлів/тек, які читати; звідки брати конвенції>
ПРИЙМАННЯ: <механічна перевірка, яку ти сам запускаєш перед звітом:
  команда тесту/скрипта/grep і очікуваний результат>
ФОРМАТ ВІДПОВІДІ: <список файлів + результати перевірок + що пропущено>
ЗАБОРОНИ: <push, деплой, зміна конфігів, вигадування фактів; «не знаєш — спитай/позначай»>
```

### Поганий бриф → добрий бриф

Погано: «Напиши специ для фабрик у src/queries». (Немає зразка, критерію,
меж — виконавець вигадає стиль і "перевірить" на око.)

Добре: «Для КОЖНОЇ фабрики *.ts у src/queries/** без відповідного .spec.ts
створи спеку за стилем src/lib/to-data-table.spec.ts: фікстура з ключів
columnMetadata самої фабрики; перевір connection, непорожній query з EVALUATE,
збіг ключів; assertion на mark — лише якщо фабрика експортує vegaLiteSpec.
ПРИЙМАННЯ: npx vitest run — усі зелені. НЕ чіпай самі фабрики. Звіт: список
створених файлів + кількість тестів.»

### Правила брифування

1. Критерій приймання виконавець запускає **сам** і звітує результатом — не «я
   думаю, що готово».
2. Виконавець, що впирається в неоднозначність, **зупиняється і питає** (або
   позначає припущення явно) — не вгадує. Це прописано в exec-* агентах.
3. Фактів у брифі більше, ніж свободи: шляхи, приклади, зразковий файл.
4. Один бриф — один результат. «Зроби А, а ще глянь Б» = два брифи.

## §5. Верифікація

### Три типи, за зростанням вартості

1. **Механічна** (тести, компілятор, валідатор, скрипт-діф) — завжди перша,
   обов'язкова для будь-якого коду. Ніколи не пропускається «бо агент сказав ок».
2. **Скептик** (`verify-skeptic`, 1 агент, effort high/xhigh) — для тексту,
   логіки, конфігурацій перед публікацією. Бриф — «спростуй»: знайди, що
   зламано, з конкретним фіксом на кожну знахідку.
3. **Панель** (3+ незалежні скептики з різними лінзами, голосування) — лише
   коли ціна помилки максимальна І механіки немає (наприклад, реліз методології,
   якою користуватимуться інші).

### Правила

- Автор ніколи не верифікує себе — навіть топ-модель.
- Верифікатор ≥ рівня автора; дешевша модель «перевіряє» дорожчу лише формально.
- Знахідки скептика передаються fix-агентам **дослівно** («заміни рядок X на Y»),
  без «подумай над цим» — інакше фікс породжує нові варіації.
- Після фіксів: механічна перевірка повторюється завжди; повторний скептик —
  лише якщо фікси зачепили логіку, а не текст.

## §6. Фази і паралелізм

**Розвідка → План → Фан-аут → Верифікація → Інтеграція.**

- Розвідка і план — головний контекст (план на топ-моделі; розвідка — дешеві
  інструменти: Glob/Grep/скрипти).
- Фан-аут: незалежне — паралельно; залежне — конвеєром (елемент А на кроці 3,
  поки Б на кроці 1). **Бар'єр** (чекати ВСІ результати) — лише коли наступний
  крок реально потребує всіх: дедуплікація знахідок, «порівняй варіанти»,
  early-exit «нічого не знайдено — далі не йдемо».
- Інтеграція — завжди головний контекст: зшивання, конфлікти, відповідальність.

## §7. Економіка

- Overhead запуску агента: ~10–15k токенів (системний промпт + бриф + вхідне
  читання). Задача, яку головний контекст зробить за <10k, делегуванням лише
  дорожчає.
- Беззбитковість делегування вниз: (вартість_виконавця + бриф + верифікація)
  < (вартість_топ_моделі × токени_задачі). За відносних цін §3 делегування
  haiku окупається на механічних задачах від ~30–50k токенів роботи АБО коли
  паралелізм критично ріже стінний час.
- Паралелізм не здешевлює — він пришвидшує. Сумарні токени ті самі або більші;
  платите за стінний час і за незалежність суджень.
- Орієнтир з реальної практики: повний аудит+верифікація+фікси екосистеми
  (5 репо) ≈ 1.5M токенів агентної роботи. Правка одного опису скіла ≈ 5k у
  головному контексті. Оркеструвати друге — безглуздо.

## §8. Готові рецепти

### Р1. Реліз скіла в marketplace
Розвідка (сам: diff, зачеплені плагіни) → правки (сам або exec-sonnet за
шаблоном) → механіка (validate_repo.py) → `verify-skeptic` (спростуй описи,
крос-посилання, версії) → фікси → validate знову → PR. Merge — після зеленого CI.

### Р2. Зміна схеми БД (Rayfin-проєкти)
План (топ: інваріанти) → schema-reviewer (sonnet) → security-auditor (sonnet)
→ schemaPolicy-тести (механіка) → docs у тому ж коміті → deploy-checklist.
Це вже закодовано в проєктному скілі schema-change.

### Р3. N однорідних файлів (специ, конвертації)
План+шаблон+критерій (топ, один раз) → exec-haiku партіями по 5–10 з механічною
перевіркою після кожної партії → зелений прогін усього → інтеграція.

### Р4. Аудит репозиторію/екосистеми
Розвідка (сам: скоуп, список об'єктів) → фан-аут читачів по лінзах (sonnet,
schema на відповідь) → бар'єр → синтез (головний контекст) → скептик на
висновках → звіт.

### Р5. PR-ревʼю чужої роботи
pbip-pr-reviewer / code-review (sonnet, за рубрикою) → знахідки з file:line →
верифікація знахідок (топ або механіка) → коментарі. Без фан-ауту: один PR —
один рев'ювер, панель лише для релізних PR.

## §9. Чесність і журнал

- Підсумок оркестрованої роботи завжди називає: хто що робив (рівні), що
  перевірено механічно (команди й результати), що перевірено скептиком
  (кількість знахідок/фіксів), що свідомо пропущено й чому.
- Виконавці звітують «зроблено X, пропущено Y, припущення Z» — приховане
  пропущене в оркестрації розмножується мовчки.
- Якщо агент повернув порожнє/дивне — читайте його журнал перед повторним
  запуском; не запускайте вдруге наосліп.
