Онови власні скіли в маркетплейсі й оформи реліз. Аргументи: `$ARGUMENTS`
(назви скілів для `--apply`; порожньо — усе, що розійшлось).

Це ритуал «Оновити власний скіл у маркетплейсі» з CLAUDE.md плюс облік
випуску в тій формі, яку тримають записи CHANGELOG.

## 1. Перенести з майстер-копій

Джерело правди для власних скілів — `~/.claude/skills`: вони правляться під
час роботи, а репозиторій є знімком для інших. Напрямок публікації один:

```bash
python scripts/sync_from_local.py                   # хто розійшовся з майстер-копією
python scripts/sync_from_local.py --apply <скіл>    # перенести названі
python scripts/sync_from_local.py --apply-all       # перенести все, що розійшлось
```

Скрипт дорогою знеособлює локальні шляхи (плейсхолдер замість шляху до
проєкту), а якщо після цього конкретика лишилась — зупиняється й називає
файл: виправ його руками, не доводячи справу до CI. Скіли з навмисною
різницею (`icon-set-manager` тримає локально справжні шляхи,
`pbi-corporate-theme` — логотипи) перелічені в самому скрипті й ніколи не
переносяться; тека `logos` відсіюється.

**Зворотний напрямок — тільки руками й прицільно.** Якщо новішим виявився
репо (наприклад, там уже знеособлений приклад, а локально ще стара назва),
правити треба локальну копію: `--apply-all` у зворотний бік поверне в
публічне саме те, що звідти прибирали.

## 2. Що зачеплено

`git status` і `git diff --stat`: зачеплений плагін — це `plugins/<плагін>/`
у шляху. Кроки 3–5 робити для кожного зачепленого плагіна; незачеплені не
чіпати.

## 3. Версії — в обох маніфестах

Підняти версію плагіна в **обох** файлах, однаково:

- `plugins/<плагін>/.claude-plugin/plugin.json` → `"version"`;
- `.claude-plugin/marketplace.json` → запис цього плагіна → `"version"`.

Розсинхрон ловить валідатор.

## 4. CHANGELOG

Новий запис угорі `CHANGELOG.md` за формою наявних:

```
## X.Y.Z — YYYY-MM-DD
```

- `X.Y.Z` — наступний номер випуску маркетплейсу (верхній заголовок + 1 в
  останньому числі); дата — сьогоднішня.
- Тире **довге** (`—`): `build_catalog.py` читає CHANGELOG регуляркою
  `^##\s+([\d.]+)\s+—\s+(\S+)`, інакше запис мовчки не потрапляє на сайт.
- Пункти — що змінилось у скілах, по суті, українською.
- Останній пункт — `- Версії: <плагін> <версія>, <плагін> <версія>.` — усі
  плагіни, версію яких підняли в кроці 3.
- CHANGELOG **не цитує те, що прибирає**: запис про чистку, який називає
  видалені імена, повертає їх у бандл сайту.

## 5. Сайт: описи й README

- Змінився `description` у фронтматтері скіла або зʼявився новий скіл —
  оновити/додати українську підказку в `scripts/uk_descriptions.json` (ключ =
  назва скіла; одне речення: що робить, коли корисний). Без неї на картці
  буде англійський опис.
- Змінилась кількість скілів у плагіні — поправити число в колонці Skills
  таблиці «Plugins» у `README.md` і, за потреби, текст «What it owns».
- `site/src/catalog.json` не правити руками — його перегенеровує CI.

## 6. Перевірка

```bash
python scripts/validate_repo.py
```

Має надрукувати `OK: … скілів, … плагінів`. `sync_from_local.py` запускає
валідатор сам після перенесення, але після зміни версій і CHANGELOG його треба
прогнати ще раз. Додатково `git grep -i` за залишками конкретики —
регістронезалежно, завжди. З `FAIL` не комітити: виправити й повторити.

## 7. Коміт

За розділом Git у CLAUDE.md: перший рядок як у наявних записах
(`X.Y.Z: <що зроблено>`), деталі в тілі українською, `git commit -F <файл>`
для багаторядкового повідомлення. Наприкінці — короткий звіт: які плагіни на
які версії, номер випуску, результат валідатора.
